# Coding 面试题选取策略

当用户要求考察 coding 能力时，从可靠来源（首选 LeetCode，可辅以 HackerRank、CodeSignal、LintCode）选取匹配岗位与候选人特点的题目。

## 先定义评估目标

不要直接从难度或“高频题”开始选题。先定义五个变量：

1. **岗位任务原型**：日常工作究竟是算法推理、数据处理、API/服务、前端状态、并发、ML 管线、科学计算，还是代码维护。
2. **级别**：初级看正确性与可学习性；中级看边界、复杂度与工程质量；高级看问题定义、权衡、测试和演进，而不是简单增加 Hard 比例。
3. **技术栈**：语言、运行环境、允许使用的标准库、是否需要 SQL/Notebook/IDE。
4. **面试形式**：现场 coding、结对编程、代码审查、调试、take-home 或工作样本。
5. **时间预算**：留出 20%-30% 时间用于澄清、测试、优化与复盘。题目本身不应占满全部时间。

## 六维选题矩阵

每个候选题按 0-2 分打分，总分低于 8/12 不采用：

| 维度 | 0 分 | 1 分 | 2 分 |
|------|------|------|------|
| 工作相关性 | 纯谜题 | 间接相关 | 映射高频真实任务 |
| 级别区分度 | 过易/过难 | 只能区分部分水平 | 有基础解和高级扩展 |
| 可观察性 | 只看最终答案 | 可看部分过程 | 可观察澄清、设计、编码、测试 |
| 公平性 | 依赖冷知识 | 少量特定背景 | 题面自足、允许合理澄清 |
| 可追问性 | 无自然扩展 | 一个扩展 | 有复杂度、边界、规模或工程扩展 |
| 可评分性 | 主观 | 部分标准 | 有明确 rubric 与锚点 |

## 岗位到任务原型

| 岗位 | 优先任务 | 次要任务 | 不宜过度依赖 |
|------|----------|----------|----------------|
| 后端 | 哈希/队列/缓存、API 数据处理、并发安全 | 树图、系统设计 | 偏数学谜题 |
| 前端 | 状态转换、树遍历、异步流程、组件数据处理 | DOM/性能调试 | 与浏览器无关的 Hard DP |
| 数据工程 | SQL、流批处理、去重、窗口、DAG | Python 数据处理 | 纯链表技巧 |
| 数据科学 | 数据清洗、统计、实验、向量化 | SQL、模型评估 | 只考手写复杂算法 |
| ML 工程 | 特征/推理管线、批处理、缓存、模型服务 | 数值稳定性、监控 | 只考模型理论 |
| 生物信息/科学计算 | 序列、区间、图、矩阵、数值边界 | 文件解析、性能优化 | 与领域完全脱节的题 |
| 平台/SRE | 日志处理、限流、调度、并发、图 | 系统设计、脚本 | 只考白板算法 |
| 移动端 | 状态、缓存、离线同步、异步 | 数据结构、调试 | 后端规模题替代客户端能力 |
| 安全工程 | 输入解析、权限图、审计日志、威胁建模 | 安全代码审查 | 只背漏洞名称 |

## 难度与级别

- **初级**：一题 Easy/基础 Medium + 清晰测试。重点是澄清、正确性、可读性、接受提示后的学习速度。
- **中级**：一题 Medium 或真实工作样本。要求合理复杂度、边界测试、结构清晰、能解释取舍。
- **高级 IC**：Medium 主体 + 规模/并发/可靠性扩展，或代码审查/调试。重点是建模与演进，不默认使用 Hard。
- **负责人/架构师**：短 coding sanity check + 系统设计/代码审查。除非岗位日常高度算法化，不用 Hard 题替代架构判断。
- **研究/算法岗**：可用 Medium/Hard，但必须映射到实际算法能力，并允许讨论证明、近似、复杂度与实验验证。

## 面试形式选择

| 形式 | 最适合观察 | 建议时长 |
|------|------------|----------|
| 现场 coding | 问题拆解、基础实现、沟通 | 45-60 分钟 |
| 结对编程 | 协作、反馈响应、代码演进 | 60-90 分钟 |
| 代码审查 | 高级工程判断、风险识别 | 45-60 分钟 |
| 调试任务 | 定位能力、工具使用、假设验证 | 45-75 分钟 |
| Take-home | 完整度、测试、文档、设计 | 候选人实际投入建议 2-4 小时 |
| 工作样本 | 岗位真实任务 | 60-120 分钟或限时带回 |

若岗位日常很少实现算法，优先代码审查、调试或工作样本，而不是 LeetCode。

## 获取题目的方法

1. 先从官方精选列表与标签检索：LeetCode Top Interview 150（https://leetcode.com/studyplan/top-interview-150/）、LeetCode Study Plans（https://leetcode.com/studyplan/）、HackerRank Interview Preparation Kits（https://www.hackerrank.com/interview/preparation-kits）。
2. 确认题目信息：题号、标题、难度、标签、题面要点、示例。
3. 为每道题补充：考察点、期望解法复杂度、追问方向（如「能否优化到 O(n)」「空间能否 O(1)」「边界情况」）。
4. 引用来源：在输出中标注题目来源与链接，保证可追溯；若改编题面，仍保留原题链接并说明改编内容。
5. 检查题目泄漏风险：避免使用过度知名且仅凭记忆即可作答的题作为唯一证据；可更换数据结构、接口或业务约束。

## 推荐题目类别（按岗位）

| 岗位领域 | 优先标签 | 示例方向 |
|----------|----------|----------|
| 后端 / 通用 | 数组、哈希表、字符串、树、DP | 两数之和、最长无重复子串、LRU 缓存、二叉树遍历 |
| 算法 / 数据 | 排序、二分、图、DP | 合并区间、搜索旋转数组、岛屿数量、最长递增子序列 |
| 生物信息 / 序列 | 字符串、双指针、滑动窗口、图 | 最长公共前缀、DNA 序列、字符串匹配、序列比对简化 |
| 前端 | 数组、栈、递归、树 | 有效括号、扁平化嵌套数组、深度优先遍历 |
| 数据工程 | SQL、哈希、堆、窗口、图 | 去重、Top-K、会话窗口、依赖排序 |
| ML 工程 | 数组/矩阵、堆、缓存、批处理 | Top-K、稀疏特征、批量推理调度、LRU |
| SRE / 平台 | 队列、堆、哈希、并发、图 | 限流器、任务调度、日志聚合、依赖检测 |

## 题组设计

每次面试优先设计“主问题 + 递进扩展”，而不是多个互不相关的短题：

1. **基线层**：候选人能实现正确的直接解。
2. **优化层**：讨论时间/空间复杂度与数据规模。
3. **工程层**：增加错误处理、测试、接口、可读性或并发约束。
4. **迁移层**：把算法迁移到岗位业务场景，观察是否理解而非背题。

准备一个等价备用题，以应对候选人见过原题或题目不适配。

## 可复用题目起点

以下题目只能作为选题起点，必须结合岗位改编并按六维矩阵评分：

| 题目 | 可映射岗位 | 典型扩展 |
|------|------------|----------|
| [LRU Cache](https://leetcode.com/problems/lru-cache/) | 后端、平台、ML 推理 | 并发、分布式缓存、淘汰指标 |
| [Top K Frequent Elements](https://leetcode.com/problems/top-k-frequent-elements/) | 数据工程、ML、日志分析 | 数据流、近似算法、内存受限 |
| [Repeated DNA Sequences](https://leetcode.com/problems/repeated-dna-sequences/) | 生物信息、科学计算 | 模糊碱基、长序列、滚动哈希 |
| [Merge Intervals](https://leetcode.com/problems/merge-intervals/) | 调度、基因区间、时间序列 | 流式输入、区间注释、并行合并 |
| [Number of Islands](https://leetcode.com/problems/number-of-islands/) | 图像、空间数据、生物网络 | 大矩阵、并查集、分块处理 |
| [Course Schedule](https://leetcode.com/problems/course-schedule/) | 工作流、数据管道、构建系统 | 动态依赖、循环定位、并行调度 |
| [Minimum Window Substring](https://leetcode.com/problems/minimum-window-substring/) | 文本、序列、事件窗口 | 流式数据、字符权重、近似匹配 |

不得把这张表当固定题库。若候选人明确做过同题，应切换备用题或增加真实工作约束，避免把记忆答案误判为能力。

## 评分量表

总分建议 20 分，避免只看是否 AC：

| 维度 | 分值 | 观察点 |
|------|------|--------|
| 问题澄清与建模 | 0-4 | 主动确认输入、约束、边界与目标 |
| 解法与复杂度 | 0-4 | 正确性、复杂度、替代方案与取舍 |
| 实现质量 | 0-4 | 命名、结构、语言熟练度、可维护性 |
| 测试与调试 | 0-4 | 主动构造用例、定位错误、验证假设 |
| 沟通与反馈 | 0-4 | 清晰表达、接受提示、协作与复盘 |

评分必须预先定义“通过锚点”。例如中级岗位通过要求：总分至少 13/20，且“解法与复杂度”“测试与调试”均不低于 2 分。

## 输出格式

每道题输出：

```
题目：<题号> <标题>（<难度>）
标签：<标签列表>
考察点：<核心算法 / 数据结构>
期望复杂度：<时间 / 空间>
追问方向：<优化、边界、扩展>
预计用时：<分钟>
面试形式：<现场/结对/审查/调试/take-home>
评分量表：<本题维度与通过锚点>
允许提示：<按顺序给出的降阶提示>
来源：<LeetCode 链接>
选题目理由：<与岗位 / 候选人特点的匹配说明>
```

## 注意事项

- 不要只给题号，要给出题面要点与考察点，便于面试官直接使用。
- 追问方向要具体（如「数组有序时如何优化」「数据流场景怎么做」），而非泛泛「再想想」。
- 若候选人经验与岗位要求明显不匹配，调整难度并说明理由。
- 题目来源必须真实可查，避免编造题号或链接。
- 不根据“候选人年限”机械提高难度；高级岗位重点应转向设计、权衡、测试与演进。
- 不使用与岗位无关的竞赛技巧作为淘汰门槛。
- 所有候选人使用等价题组与同一评分量表；提示应预先设计并记录。
